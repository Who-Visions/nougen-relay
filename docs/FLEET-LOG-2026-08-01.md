## 02:17Z — relay shards — the vault transport is now a command, not a one-off script

2026-08-01 (whoart, claude-cli). NouGenRelay v1.0.0+ gained `relay shards` — src/nougen_relay/shardlog.py, registered via build_parser's register(sub) pattern alongside rules.py, plus the relay_shards MCP tool and a line in the agy SKILL.md next to relay_create.

WHY IT EXISTS: the registry travels, the vault does not. Claims and legs are tracked in git so every box sees them; what a box LEARNED sits in ~/.nougen/shards, which no other machine can open. The first relay (2026-07-31, FLEET-LOG-2026-07-31.md, 11 shards) was run by hand from a throwaway script — the operation existed exactly once and left nothing behind to repeat it. The saying "Relay the shards!!!" specifies "generated BY SCRIPT"; there was no script.

USAGE: `relay shards --dry` (read vault, write nothing) / `relay shards` -> writes docs/FLEET-LOG-<utc-date>.md, then commit+push and pass the baton. Flags: --since, --vault (or $NOUGEN_VAULT), --out, --date, --exclude TITLE|HASH (repeatable), --include-tagged.

FOUR DESIGN RULES, each one a mistake already made:
1. GENERATED, NEVER RETYPED. Bodies copied verbatim from shards.content. The ONLY edit is demoting the shard's own headings one level (skipping code fences) — the hand-run log let a shard's `## VERIFIED LIVE` render as a top-level log entry, so the shard's structure impersonated the log's.
2. PUBLISHED EXACTLY ONCE, and the cutoff is not local state. Each log ends with `<!-- relay-shards through=<iso> machine=<m> -->`; the next relay reads the max marker across docs/FLEET-LOG-*.md, so it can run on a DIFFERENT BOX. Pre-marker logs fall back to parsing `## HH:MMZ — ` headings (content headings never match that shape). That fallback only has MINUTE precision, so a shard captured at 23:45:10 sits after a 23:45:00 cutoff. Resolution: round the cutoff DOWN and de-duplicate by TITLE against every existing log — re-offering a shard is caught, skipping one would be silent and permanent. Titles under "Not included here" count as published too: naming a withheld shard WAS the disclosure, and copying its body later would quietly reverse that decision.
3. NOT EVERYTHING TRAVELS. WITHHELD_TAGS = brand, positioning, personal, family, finance, legal, medical. Those shards are NAMED in the log with a pointer to recall_memory and left in the vault — a code repo is the wrong home for them even when the repo is private. --include-tagged is the deliberate override.
4. SECRET VALUES BLOCK THE WRITE (exit 1, nothing written). Patterns match the SHAPE of a credential, not the word: sk-, gh[pousr]_, AKIA, xox[baprs]-, hf_, AIza, PRIVATE KEY blocks, and (secret|token|password|api_key|client_secret)\s*[:=]\s*<24+ chars>. `wrangler secret put TWITCH_CLIENT_SECRET` is a variable NAME and must not trip it — a scan that cried wolf would be switched off inside a day. --exclude drops one bad shard instead of blocking the whole relay.

BUG FOUND BY THE EXISTING SUITE: `DEFAULT_VAULT = Path.home() / ...` at MODULE SCOPE crashed `relay --help` on any box with no HOME — test_entry_point runs the CLI with a stripped env, and because build_parser imports the module, an import-time expanduser() took the WHOLE CLI down, not just the new subcommand. Fixed: the default is the string "~/.nougen/shards", expanded inside vault_paths() with RuntimeError caught. Lesson: anything a parser imports must be importable in a hostile environment.

TESTED (tests/test_shardlog.py, 22 tests, suite 145 passed): the scan is tested by asserting it BLOCKS and that a variable name does not trip it — same discipline the Antigravity hook lesson demanded after two silent-no-op guards. Also: verbatim bodies survive byte-for-byte, fences are left alone, missing vault fails LOUDLY (silence would be indistinguishable from "nothing new" and the fleet would quietly stop receiving knowledge), and "nothing new" exits 0 so the command is usable from a hook.

## 02:20Z — Review: NouGenShards PRs #64 / #65 — one regresses privacy, one is the capability NouGenRelay lacks

2026-08-01T00:22Z (whoart, claude-cli). Deep read of both open PRs on the PUBLIC repo Who-Visions/NouGenShards, requested by GM. Captured to the vault because the review previously existed ONLY as a git handoff record (.handoffs/20260801T002255Z__whoart__claude-cli.md) — the baton carried it, the memory did not, so recall_memory could not find it.

PR #64 — DO NOT MERGE AS-IS. feat(brain-scan): read SQLite memory stores instead of ingesting them raw. +1229/-180, 14 files. The feature (sqlite_sources.py) is worth having. The problem: the branch predates PR #61, which landed the same day and UNTRACKED CLAUDE.md and GEMINI.md from the public repo. #64 adds ~150 lines across those two files, so merging it recreates them publicly — republishing the private agent operating docs, including the GM's real name in GEMINI.md line 7. GitHub reported mergeable=UNKNOWN, likely conflicting on exactly those files. FIX: rebase onto current main and DROP the CLAUDE.md/GEMINI.md hunks; the brain-scan work is separable and should land alone.

PR #65 — SOUND, recommend merge. feat(handoffs): machine identity, cross-machine sync, triggers. +2031/-21, 8 files, mergeable, 2 test files. Verified good: triggers.json EXCLUDED from sync by default with the reason written in-band ("the trigger registry is executable configuration and does not travel between machines by default") — a rule arriving from another box would run commands here; handoffs.db excluded too (derived, rebuildable from JSON, so no shared index means no concurrent-write conflict); machine.py strips the mDNS suffix (.local/.lan/.home/.localdomain) — phoebus solved this BEFORE whoart hit the identical bug in NouGenRelay the same day and fixed it independently, two machines converging separately; NOUGEN_MACHINE_PRIVATE=1 drops account name and working directory because records get pasted into issues; machine_id hashes hostname+OS+arch NOT the MAC, with the reasoning recorded (randomized MACs would change the id between runs); _execute() "never raises — a broken rule must not lose a handoff", fail-soft like every other guard in this fleet.

THE ONE THING TO SAY OUT LOUD ABOUT #65: triggers run via subprocess with shell=True (foreground and a backgrounded Popen with start_new_session=True). While triggers.json stays local that is fine — it is git-hook-equivalent, you execute rules you wrote. But --share-triggers flips it into REMOTE CODE EXECUTION BY DESIGN: a rule authored on phoebus would run in a shell on whoart. The docs call it "if you intend to distribute rules", which undersells it. Recommend keeping the default (never shared) and rewording the flag's help to say plainly that it executes other machines' commands on this box. Not a blocker — opt-in and documented — but it should be named for what it is.

STATUS: neither PR is in v1.2.0, cut 2026-07-31 (48 commits behind since 2026-06-15; v1.1.0 shipped the fail-open exposure guard and could not even install due to mcp 2.0). If #65 merges it is worth a v1.2.1.
