**What the source leg asks:**

Move `shards_recall` from model-initiated (opt-in, non-deterministic) to pipeline-initiated, so a lane with no memory instructions in its prompt still gets relevant prior shards on a cold turn — closing the one real gap vs. Anthropic's built-in vendor memory (fires with zero calls).

Three candidate layers, in order of leverage:
1. **Gateway-side pre-turn hook (preferred).** Blade's shard gateway intercepts the inbound turn, runs a cheap `shards_recall` on the user message, and prepends top-N hits (capped, ~3 hits / fixed token ceiling) as a provenance-marked context block before the model sees anything.
2. **MCP resource auto-injection.** Expose recall results as an MCP resource pulled on session/turn start instead of a tool the model must invoke. Check per-surface support.
3. **Per-lane bootstrap.** For lanes controlled end-to-end (Kaedra, local Ollama), bake the recall call into the session preamble script — cheapest, narrowest coverage, stopgap while (1) lands.

**Design constraints (from source leg):**
- Fail open, never block — gateway down means a normal turn with no memory block and a one-line note; recall latency must never gate the response.
- Keep the write path explicit — auto-recall on read only; capture stays deliberate.
- Preserve provenance in the injected block — era, source store, id, `[amended]`/`[retracted]` flags — so injected hits round-trip into `shards_mark`/`shards_amend`.
- Feed the loop — `shards_mark` any injected shard that demonstrably shaped the answer.

**Risk noted by relay-watch:** whichever layer ships first must satisfy all of the above constraints simultaneously, or auto-recall regresses the exact advantage (auditable, retractable, provenance-tagged memory) that shards currently has over vendor memory.
