## What the source legs ask (read in order)

### 1. [20260828T183639Z__chatgpt-app__g-whoentertains] — TOP 0.01% arXiv scanner rebuild: event-driven RSS ingest with idempotency, version lineage, scoring, and autonomous research handoff

Foundational rebuild spec: RSS fetcher (conditional GET, backoff, fetch ledger), namespace-aware XML parser (never regex), idempotency/version lineage (paper vs paper-version event, GUID identity), checkpointing (only after durable write), a weighted research scorer, two-stage summarization (cheap triage, expensive memo only for high-value papers), version diffing on replacements, SHARD/RELAY/BOTH/IGNORE policy, a SQLite-first DB model (feeds/papers/paper_events/research_scores/research_memos/dead_letters/scanner_runs), a Python asyncio skeleton, a chaos/crash-safety test list, Pulse observability fields, and security/quality requirements (XML entity protection, log sanitization, provenance-mandatory). 10 acceptance criteria including zero-duplicate replay and unattended reboot resumption.

### 2. [20260828T183735Z__chatgpt-app__g-whoentertains] — Extend arXiv scanner with official feed topology, category composition, scheduling, and RSS/ATOM fallback

Adds: RSS+ATOM dual support per subject area, canonical feed URL bases, single/multi-category (`+`-joined) feeds with the documented 2000-result ceiling handled by deterministic splitting, a declarative `ArxivFeed` registry (dataclass sketch included) instead of hardcoded URLs, per-feed state tracking (ETag/Last-Modified, 304-as-success), a priority-ordered async poll loop, low-frequency scheduling around arXiv's daily Eastern-midnight cadence, `source_degraded` telemetry when feeds lag, and keeping the RSS/API/shard-grid roles separate. 8 acceptance tests.

### 3. [20260828T183850Z__chatgpt-app__g-whoentertains] — Validate live arXiv CS feed endpoint against scanner contract

Confirms the canonical live cs.AI/cs archive RSS+ATOM URLs and flags a real integration quirk found from the ChatGPT/web environment: a plain fetch rejected `application/rss+xml` as unsupported, so the scanner must use a real HTTP/XML client (not an HTML-only fetch abstraction) and explicitly accept rss+xml/atom+xml/xml/text-xml. Lists concrete fetch/parse/checkpoint/Pulse-metric requirements and 5 acceptance tests (raw fetch succeeds, wrong content-type doesn't silently pass, RSS-outage falls back to ATOM, etc.).

### 4. [20260828T183957Z__chatgpt-app__g-whoentertains] — Complete arXiv scanner contract with API access policy, enrichment lane, and attribution safeguards

Adds compliance/attribution requirements for using arXiv's API as an enrichment lane behind the RSS discovery heartbeat: required attribution text, a prohibition on branding that implies arXiv endorsement, a review gate before any commercialized use, and config for user-agent/contact/attribution/request-budget/API-fallback-health. Acceptance: daily RSS runs without API spam, enrichment limited to scored papers, survives an API outage via queued enrichment, and exposes compliance/attribution status in telemetry.

### 5. [20260828T184135Z__chatgpt-app__g-whoentertains] — Harden arXiv API client around official Atom query contract

Full implementation spec (with a runnable Python sketch) for the `export.arxiv.org/api/query` enrichment client: Atom 1.0 + opensearch + arxiv-extension namespace parsing, canonical-id-from-entry-id identity, deterministic pagination via totalResults/startIndex/itemsPerPage, and production requirements (timeout/backoff/jitter, query+cursor caching, raw-response provenance hashing, version-append-never-overwrite, unit tests against fixture payloads including malformed/empty/paginated cases, and Pulse metrics).

### 6. [20260828T184318Z__chatgpt-app__g-whoentertains] — Use cs.AI recent listing as scanner verification and relevance benchmark

Proposes using the human-facing arxiv.org/list/cs.AI/recent page as an independent cross-check surface (counts/dates/ids/titles/ordering) against RSS+API ingestion, verification/fallback only -- not the primary ingestion path.
