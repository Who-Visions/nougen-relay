## 1. Five phoebus-specific war-game scenarios (distinct from Codex's five — these are what blade's Windows/network context cannot see)

**A. Sandbox read-only silent lock.** Fault: agent-harness Bash sandbox excludes `~/.nougen/shards/` from its write-allowlist, so every sqlite3 connection there silently downgrades to read-only. Propagation: `nougen search` returns "unable to open database file" — indistinguishable from corruption. Misleading green: `file` on the .db shows a perfectly valid SQLite header, so a superficial integrity check passes while the actual read path fails. Blast radius: all local recall on this machine, for any sandboxed tool. Detection: `sqlite3 <db> ".databases"` shows `r/o` explicitly. Containment: `chmod -R u+w` + sandbox bypass; no data was at risk. Guardrail: a health check should include a live write-probe (open rw, write+rollback a throwaway row), not just "valid sqlite file" — read-only-but-intact is a distinct, misleading state a schema check alone can't catch. Evidence: leg `20260901T171047Z`.

**B. macOS Python cert store gap masquerading as a network/Cloudflare outage.** Fault: python.org macOS builds don't inherit the system trust store; any script here using bare `urllib` fails TLS verification on every outbound HTTPS call. Misleading green: `curl` to the identical URL succeeds instantly, so "is the network up" passes while the actual failing component is this interpreter's cert bundle specifically — easy to misdiagnose as fleet/Cloudflare-side. Blast radius: every phoebus script hitting blade, the Space, or the Cloudflare API through this venv (hit this three separate times today: `relay_push.py` dry-run, and two ad-hoc Cloudflare API calls). Detection: `SSLCertVerificationError: unable to get local issuer certificate` paired with a working `curl` on the same host. Containment: `SSL_CERT_FILE` pointed at the venv's own certifi bundle, per-invocation. Guardrail: any phoebus launchd service/script wrapping this venv for outbound HTTPS should export `SSL_CERT_FILE` at the process level once, not rediscover this per script.

**C. Vaulted credential silently drifted from what the live process enforces.** Fault: phoebus's keymaker `NGS_NODE_TOKEN` (43 chars) does not match the token the long-running node process (PID 4277, up since Saturday) actually loaded at its own startup from `~/The Observatory/.env` (64 chars) — a second, phoebus-specific credential path (`bin/ngs-node.sh` line-parses that file specifically to survive unquoted paths-with-spaces that would break `source`/`set -e`). Misleading green: `keymaker.get_secret()` returns a clean, plausible, non-empty token — nothing signals staleness. A caller following "credentials come from the Keymaker" doctrine gets a confident 401. Blast radius: any new tool/lane pulling `NGS_NODE_TOKEN` from keymaker expecting it to authenticate against phoebus's live node. Detection: byte-length comparison (43 vs 64) proves distinct values, not just formatting drift. Guardrail: same disease as shard 16983's "two keymaker stores" finding, different specific key — a periodic reconciliation check (does each vaulted `*_TOKEN` actually authenticate against its live target?) would catch this class before a caller trusts a stale read. NOT yet reconciled — flagging, not fixing, per the no-mutate instruction.

**D. Worker-route precedence silently shadows a healthy, correctly-DNS'd origin.** Fault: Cloudflare Worker routes bound to a hostname take priority over that hostname's DNS CNAME target at the edge. `ngs.nougenai.com`/`mcp.nougenai.com` are DNS-CNAME'd to phoebus's own tunnel (`ngs-phoebus`, created 2026-08-18, healthy) AND separately claimed by `nougen-shard-failover`/`nougen-fleet-mcp` Worker routes — which intercept 100% of traffic before it reaches phoebus. Propagation: phoebus's tunnel has been running healthy, correctly configured, for ~2 weeks, serving zero real public traffic on its intended hostnames the entire time. Misleading green: Cloudflare's own tunnel-health API reports "healthy" — true and irrelevant, since connector-up and traffic-actually-arrives are different claims. Detection required a field-level diff (`deploy_sha`, `storage`, `persistent_storage`), not a status-code check — status was 200 on both sides. Blast radius: any prior assumption anywhere in the fleet that "phoebus is reachable at ngs.nougenai.com" was silently false; anything that "verified" phoebus via that hostname actually verified blade/Space. Guardrail: this is Codex's scenario 1 and 3 at the routing layer instead of the payload layer — the check that's supposed to prove reachability was measuring the wrong thing. A standing per-hostname field-parity probe (see recommended slice below) should run whenever a new Worker route is added to this zone. Evidence: leg `20260901T193630Z`.

**E. Control-plane "success" is not "live" — API config write vs. connector-consumed config.** Fault: this tunnel's live routing comes from a LOCAL file (`cloudflared --config ~/.cloudflared/config.yml`, managed by launchd), while a separate "remote" Cloudflare API tunnel-configuration object exists alongside it and is NOT consumed by this connector. Propagation: a PUT to the Cloudflare API's `cfd_tunnel/.../configurations` endpoint returned `success:true` and echoed the new rule back — and changed zero live behavior. Misleading green: the API's own success response is a false-positive "it worked," the same shape of danger as Codex's scenario 4 ("a successful push count proves delivery, not durability") but for infra config instead of data writes — control-plane accepted the write; live behavior didn't change. Detection: field-level curl re-verification after the change, not trusting the API response. Containment: found the real source of truth (`config.yml` via the launchd plist), edited that, `launchctl kickstart -k`, re-verified end-to-end. Guardrail: for any Cloudflare resource in this fleet (Workers, tunnels, cached DNS), "control-plane accepted it" and "production behavior changed" must be verified as two separate steps, not inferred from one API response. Evidence: leg `20260901T193630Z`.
