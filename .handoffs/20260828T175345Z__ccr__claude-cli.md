## The measured root cause (from 20260828T173959Z, the most precise of the four)

Not bidirectionally broken — one-way and batched:
1. **gateway → git: works, batched ~15 min.** Connector-created legs do land on disk with full bodies; lag is "time until the next batch," 16–748s observed.
2. **git → gateway: does not propagate state changes.** A CLI `ack`/`checkpoint` writes git only; the gateway never learns.
3. **The batch down-sync overwrites.** Any CLI-made state change sitting in git when a batch fires is destroyed, because the gateway pushes down a stale view that never included it.

**Concrete evidence of real damage**: AGY's checkpoint on the keymaker P0 fix (source leg [20260828T164002Z__claude-app__g-whoentertains] lineage) was acked via CLI at 16:59:40Z, then silently reverted to `open` by the next batch — twice, including after a manual repair from HEAD.

## The fix, in priority order

1. **Make the down-sync merge, not overwrite.** Union `relay` events by `(event, at, agent)`, take the furthest-along status, never whole-file overwrite. This alone stops the data loss without touching either registry's ownership. (from 20260828T172332Z / 20260828T173959Z)
2. **Close git → gateway write-through.** CLI `ack`/`checkpoint` must write through to the gateway, not just local git. (from 20260828T172332Z / 20260828T173959Z)
3. **Optional**: shorten the batch interval — secondary, a 15-min lag is survivable, silent destruction is not.

Assigned by the source legs to **Codex**, as part of the reconciliation/lease-loop work already in progress — "fix the merge before the lease loop: a `reconcile()` running on top of a clobbering sync will keep re-dispatching completed work no matter how correct its logic is."
